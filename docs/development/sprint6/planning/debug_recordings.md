### Root-cause analysis & resolutions (2026-07-02)

**P1 — Gravity ignores the OmniHand (RESOLVED, docs).** The `teach_manager` does not build the gravity
model; it only calls `mit_controller/freedrive` on the already-running MIT controller. The gravity model
is baked at MIT-controller bring-up. The OmniHand is folded in **only** when `effector_type:=omnihand`
(that sets `use_right_hand:=true` in the gravity URDF slice and freezes the finger joints so the hand
rides as a rigid payload). The documented teach bring-up passed only `gravity_arm_side:=right`, so the
mount (tilt) was correct but the ~1 kg hand was absent. Verified by regenerating the gravity URDF: 4.58 kg
(hand-less) vs 5.64 kg with `effector_type:=omnihand` (+1.04 kg hand, still 7 movable joints). The URDF
carries real hand inertia (palm 0.83 kg + fingers), so the machinery was complete — only the flag was
missing. Fix: `docs/control/teach_and_run.md` now requires `effector_type:=omnihand` on the bring-up
(harmless side effect: the driver merges `feedback/omnihand/joint_states` into combined feedback, no extra
CAN traffic).

**P2 — Unstable bus / bridge dies when the MIT controller starts (PARTIALLY RESOLVED, config).** Root
cause: the arm and the OmniHand share one physical bus (`can_nero_right`; only two mttcan channels exist,
one per arm — no free HW channel). Three compounding factors: (a) `ONE_SHOT=on` (no retransmission) +
the OmniHand's high CANFD IDs = low arbitration priority, so under arm load the hand loses arbitration and
its frames are dropped -> `请求超时`; idle-hold sends little, so the hand is fine there — exactly the
observed contrast; (b) no `txqueuelen` was set (kernel default 10) so a 7-frame MIT command burst overran
the TX ring -> ENOBUFS `[105]`; (c) arm MIT command TX at `control_rate_hz=100`. Fixes applied:
`scripts/activate_native_can.sh` now sets `txqueuelen` (default 1000) and keeps `ONE_SHOT` switchable
(`ONE_SHOT=off` documented as the fallback if the hand still starves). **First-test strategy (chosen):**
keep `one-shot on` + deeper TX ring, keep `control_rate_hz` at 100 Hz (a lower rate risks hold
instability), and instead run a stiffer/more-damped MIT hold (`kp` ~+50%, `kd` ~2.5x in
`nero_mit_controller_defaults.yaml`). Note: `pub_rate` is **not** a bus lever (ROS republish of cached
feedback; the arm firmware push rate is fixed). Remaining option if congestion persists: a dedicated hand
channel (USB-CAN, or the free `can_nero_left` channel in single-arm operation) — needs hardware.

**Mode arbitration — can the internal firmware controller and the MIT controller be active at once?**
No, not at the motor level: the Nero motors are in exactly one firmware-selected mode at a time
(`set_normal_mode` / `set_motion_mode('mit')` / `set_leader_mode` in `agx_arm_ctrl_single_node.py`).
`move_mit` switches the motors to MIT torque mode (once per transition); `move_j/p/l/c` use the firmware's
internal position controller — they are mutually exclusive modes, so both cannot drive a joint
simultaneously. The only continuous command publisher is the MIT node's `control/move_mit`; the firmware
`move_j`/`move_home`/`emergency_stop` paths are one-shot service calls, so there is no steady dual-source
thrash in normal operation. The single "MIT switches itself in" path is `auto_enable_on_trajectory` (MIT
node): an incoming FollowJointTrajectory goal (MoveIt) or the debug `~/joint_trajectory` topic auto-enables
MIT. In the plain teach bring-up neither source exists (no move_group running; debug topic off unless
`enable_debug_joint_trajectory_topic:=true`), and the teach manager enables MIT **explicitly** after
`set_normal_mode`, so the sequence is clean. Keep `enable_debug_joint_trajectory_topic:=false` during teach
except for the deliberate `f` playback, and do not run a MoveIt slice against the same arm while teaching.

**P3 — Overcurrent / stall (堵转) & tactile (DEFERRED).** The status message ships empty
`active_joint_currents_a` / `active_joint_temperatures_c` and `active_joint_over_current` all-false while
the SDK logs `堵转` (stall) — the SDK's stall/current signal is not wired into the ROS diagnostics or a
recovery path, and `fist_vendor_demo` drives the middle/ring fingers into collision. Follow-up: surface
per-joint current/temperature, add a stall-recovery, and add finger spread to the fist preset.
